# 관리자 디자인 규칙

> 이슈 #26 의 산출물. **2026-08-14 검토를 거쳐 확정됨** — 갈린 항목은 7장에 정리했다.
> 구현 PR 은 이 문서의 규칙 번호(예: 규칙 2-3)를 인용한다. 뒤따르는 이슈: #27(공통 뼈대) · #28(여섯 화면).

## 0. 이 문서는 왜 있나

굿퀘스천 관리자 화면 여섯은 개발자가 엔진 동작을 눈으로 확인하려고 만든 도구다. 그래서 화면에
적힌 말이 데이터베이스(DB, 자료를 표 형태로 저장해 두는 곳) 컬럼 이름 그대로다 — `story_code`,
`scope`, `started_by` 같은 것들.

그런데 이 MVP 는 해커톤에 나가고, **해커톤 운영자가 이 화면을 직접 클릭해 본다.** 운영자는 AI 를
모르고 우리 DB 도 모른다. 지금 화면은 그 사람에게 읽히지 않는다.

이 문서는 "그럼 어떻게 고칠 것인가"의 기준이다. 각 규칙에는 **왜 그런지**를 붙였다 — 근거 없는
규칙은 다음 사람이 지킬 이유가 없기 때문이다.

**읽는 순서**: 1장(진단)에서 지금 무엇이 문제인지 보고, 2장(벤치마킹)에서 남들은 어떻게 하는지 본
다음, 3~5장의 규칙을 읽는다. 6장은 인용한 출처 목록이다.

## 1. 진단 — 지금 화면의 문제

실제 코드에서 확인한 것만 적는다.

| # | 증상 | 실물 |
|---|---|---|
| 진단1 | **DB 컬럼명이 그대로 화면 라벨** | 회차 시작 폼의 다섯 칸이 `story_code`·`scope`·`scene_order`·`started_by`·`experiment_note` (`runs/page.tsx:49-82`) |
| 진단2 | **`null` 을 사람에게 보여준다** | 회차 목록의 시작한 사람 칸: `{회차.started_by ?? 'null'}` (`runs/page.tsx:169`) |
| 진단3 | **12px 고정폭 글씨가 본문** | 화면 전체가 `text-sm`(14px) 컨테이너에 안내문은 `text-xs`(12px), 값은 `font-mono` (`(admin)/layout.tsx:38`, 전 화면) |
| 진단4 | **안내문에 코드 인용이 섞인다** | "`story_sessions` 한 행과 `runs` 한 행이 함께 생기고" (`runs/page.tsx:44`) |
| 진단5 | **코드 주석용 기호가 화면 문구로 샜다** | 화면에 보이는 안내문에 `⛔ 여기서 LLM 을 부르지 않는다` (`runs/page.tsx:45`) |
| 진단6 | **말투가 화면마다 다르다** | 회차는 반말("아직 돌린 회차가 없다"), 프롬프트 작업대는 존댓말("…보여 줍니다") |
| 진단7 | **오류 메시지가 운영자가 할 수 없는 조치를 시킨다** | "`stories` 가 비었다. `npx tsx db/seed.ts` 로 시드를 넣어라" (`runs/page.tsx:118`) |
| 진단8 | **위험한 버튼과 안전한 버튼이 똑같이 생겼다** | 「시작」(LLM 호출·돈)·「기준 남기기」·「회차에 실험용으로 저장」이 전부 `border border-zinc-700 px-3 py-1` |
| 진단9 | **제품과 다른 회색 팔레트** | 관리자는 `zinc-*` 기본값, 견본(voice-test)은 `bg-surface`·`text-ink`·`shadow-panel` |
| 진단10 | **길잡이가 없다** | 머리말의 밑줄 링크 6개가 전부. 현재 위치 표시도, 각 메뉴가 무슨 화면인지 설명도 없다 (`(admin)/layout.tsx:48-54`) |
| 진단11 | **제목이 본문과 구별되지 않는다** | 화면 제목이 `h2 font-semibold` — 굵기만 다르고 크기는 본문과 같다 |
| 진단12 | **다른 두 채점을 같은 이름으로 부른다** | 회차 목록의 「위반율」(캐릭터 대사 채점)과 골든셋의 채점(분석 채점)이 화면에서 안 갈린다. `lib/judge.ts` 머리말이 이 혼동으로 실제 사고가 났음을 기록하고 있다 → 규칙 2-9 |

한 줄로: **화면이 DB 를 그대로 비추고 있고, 사람이 무엇을 하는 자리인지는 안 적혀 있다.**

## 3. 화면 배치·정보 밀도

### 규칙 1-1. DB 컬럼을 그대로 보여주지 않는다

화면에 나가는 이름은 사람이 쓰는 말이다. DB 컬럼명은 **개발자가 코드를 짤 때 쓰는 이름**이지
화면 라벨이 아니다.

| 지금 | 바꿀 것 |
|---|---|
| `story_code` | 이야기 |
| `scope` | 어디까지 돌릴지 |
| `scene_order` | 몇 번째 장면 |
| `started_by` | 시작한 사람 |
| `experiment_note` | 실험 메모 |
| `analysis_model` / `analysis_effort` | 분석에 쓸 AI 모델 / 생각 깊이 |
| `prompt_version` | 프롬프트 판 번호 |

> **근거** — 영국 정부 디자인 시스템: *"관리 화면을 설계할 때 DB 행을 그대로 화면에 뿌리고 추가·
> 보기·수정·삭제 버튼만 붙이기 쉽다. 그러지 마라. 게으른 것이다."* 관리자도 **할 일**이 있어서
> 오는 것이고, 화면은 그 할 일을 도와야 한다.

**예외 없다 — 로그 세 줄도 번역한다** (2026-08-14 결정). 지금 회차 상세의 회색 상자는 서버 터미널
로그(`lib/log.ts` 가 만든 문자열)를 **글자 그대로** 복사해 찍는다. 앞으로는 화면에 사람 말로 옮긴
문장을 보여주고, 원문은 그 아래 「개발자용 원문 보기」로 접어 둔다(규칙 1-4).

> ⚠️ **맞바꾸는 것**: 터미널 로그와 화면 글자가 달라지므로, 개발자가 두 쪽을 눈으로 대조하기가
> 지금보다 번거로워진다. 접어 둔 원문이 그 자리를 메운다. **`lib/log.ts` 자체는 건드리지 않는다** —
> 터미널 로그는 지금 형식 그대로 두고, 화면용 문장을 화면 층에서 따로 만든다.

### 규칙 1-2. 화면은 카드로 나눈다

한 화면에 할 일이 둘 이상이면 카드로 가른다. 카드 하나 = 할 일 하나.

```
rounded-3xl bg-surface p-8 shadow-panel   (견본 voice-test 의 카드)
```

각 카드는 ① 제목(20px 굵게) ② 이 카드가 무엇을 하는지 한 줄 ③ 내용 순서다.

> **근거** — 견본(voice-test)이 '대본 불러오기 / TTS / STT' 세 카드로 갈라져 있어 한 화면에서
> 할 수 있는 일이 눈에 바로 들어온다. 지금 회차 화면은 「회차 시작」과 「회차 목록」이 `<section>`
> 으로만 갈려 있어 경계가 안 보인다.

### 규칙 1-3. 글자 크기 계단을 지킨다

| 자리 | 크기 | 비고 |
|---|---|---|
| 화면 제목 | 28px 굵게 | 지금은 본문과 같은 크기다(진단11) |
| 카드 제목 | 20px 굵게 | |
| 본문·안내문 | 14~15px | **12px 를 본문에 쓰지 않는다** |
| 입력칸 안 | 16px | 그보다 작으면 모바일에서 화면이 확대된다 |
| 표 안의 값 | 14px | 열을 줄여서 맞춘다 — 글자를 줄이지 않는다 (규칙 1-5) |
| 고정폭(mono) 글꼴 | **값에만** | 아이디·모델명·시각처럼 글자 단위로 읽는 값. 설명문에는 안 쓴다 |

> **근거** — 견본은 본문 14px, 입력 16px, 제목 28px 다. 지금 관리자는 안내문까지 12px 고정폭이라
> 읽는 사람이 "이건 나한테 하는 말이 아니구나"로 받아들인다.

### 규칙 1-4. 개발자용 정보는 접어 둔다

원문 JSON, 로그 세 줄, 프롬프트 전문, DB 아이디는 `<details>` 안으로 넣고 제목을 붙인다 —
「개발자용: 이 턴의 판정 기록」처럼.

> **근거** — Google AI Studio 는 모델 설정을 접히는 옆 패널에 두고 가운데는 대화가 차지한다.
> 영국 정부 지침의 3단 사다리에서 **자료(raw data)를 다 뿌리는 것이 가장 낮은 단계**다 —
> 필요한 사람이 펼쳐 보게 하되, 기본은 감춘다.

### 규칙 1-5. 표는 「비교하는 자리」에만 쓰고, 상세는 따로 연다

표를 쓴다면 ① 찾기(정렬·거르기) ② 비교 ③ 한 줄 상세로 들어가기 를 지원한다. 셋 다 없으면
표가 아니라 목록이나 카드가 맞다.

회차 목록은 **회차끼리 견주는 것이 존재 이유**이므로 표가 맞다. 다만 지금은 정렬도 거르기도 없다.

**회차 표는 9열 → 5열로 줄인다** (2026-08-14 결정). 글자를 12px 로 줄여 다 욱여넣는 대신, 목록에는
한눈에 견줄 것만 남기고 나머지는 행을 눌러 여는 상세 화면으로 민다.

| 목록에 남길 5열 | 상세로 밀 것 |
|---|---|
| 언제 · 이야기 · 상태 · 아이가 말한 횟수 · 대사 규칙 위반 | 어디까지 돌렸는지 · 프롬프트 판 번호 · 시작한 사람 · 끝난 시각 |

> **근거** — NN/g: 표의 강점은 인접한 두 값을 눈만 움직여 비교할 수 있다는 것이고, 표 화면이
> 지원해야 할 일은 찾기·비교·한 행 보기/고치기·조작 네 가지다. 9열을 다 보여주는 것은 「비교」가
> 아니라 「DB 를 비추는 것」에 가깝다(규칙 1-1).

### 규칙 1-6. 요약 → 목록 → 상세, 세 단

목록 화면 맨 위에 그 화면의 숫자 요약을 둔다. 회차라면 「총 12회 · 오늘 3회 · 위반율 평균 4.2% ·
판정 불가 7건」 정도.

> **근거** — Microsoft waza 대시보드는 요약 카드(총 건수·통과율·토큰·비용·소요시간) → 정렬 가능한
> 표 → 행 클릭 시 상세 순서다. Braintrust 도 목록 행 → 상세(트레이스) 2단이다.

### 규칙 1-7. 제품 디자인 토큰을 쓴다

`zinc-*` 같은 Tailwind 기본 색을 직접 쓰지 않고, 제품이 정의한 이름(`bg-surface`, `text-ink`,
`text-ink-muted`, `border-divider`, `bg-primary`, `shadow-panel`)을 쓴다.

> **근거** — 결정 D9. 견본과 관리자의 생김새를 통일하면, 시연할 때 두 화면이 한 제품으로 보인다.
> 새 라이브러리는 안 들인다(D4) — Tailwind 설정에 이미 있는 이름을 쓰는 것뿐이다.

## 4. 설명문 글쓰기

**대상 독자: 일반 성인 누구나.** AI 도 IT 도 모른다고 가정한다(D7).

### 규칙 2-1. 화면마다 맨 위에 「여기는 무엇을 하는 곳인가」 배너

2~3문장. 새 용어 0개. 이 화면에 처음 온 사람이 읽고 무엇을 하는 자리인지 말할 수 있어야 한다.

```
검수
아이가 한 말에 AI 가 매긴 판정이 맞는지 사람이 다시 보는 곳입니다.
AI 가 "모르겠다"고 넘긴 것만 여기 모입니다. 여기서 판정을 고치면 AI 성적표에 반영됩니다.
```

> **근거** — 이 배너는 부모 이슈 #25 의 완료 기준이기도 하다. GOV.UK: *"제목은 뒤따르는 글의
> 목적을 설명해야 한다."*

### 규칙 2-2. 내부 용어는 없애지 말고 **처음 쓸 때 풀이한다**

'회차·시드·골든셋·프롬프트'는 팀이 실제로 쓰는 말이라 없애면 오히려 소통이 끊긴다. 대신 각 화면에서
**처음 나올 때** 괄호로 뜻을 적는다.

아래 표는 2026-08-14 인터뷰에서 사용자가 확정한 뜻이다. **이 표가 모든 화면 설명문의 기준이다.**

| 용어 | 첫 등장 시 풀이 |
|---|---|
| 회차 | 아이와 AI 가 이야기를 한 번 처음부터 끝까지 진행한 기록 |
| 시드 | 기획자가 고치는 이야기·캐릭터 설정값. 이 화면에서 한 칸씩 고치고, 다 되면 파일로 내려받아 정본으로 삼는다 |
| 골든셋 | AI 가 잘했는지 재는 **정답지**. 사람이 미리 정답을 적어 둔 문제 모음이고, **두 가지를 잰다** — ① 아이 말을 제대로 알아들었나 ② 캐릭터 대사가 아이를 잘 이끌었나 |
| 프롬프트 | AI 에게 주는 지시문. "너는 이런 역할이고 이렇게 답해라" |
| 검수 | AI 가 매긴 판정을 사람이 다시 보고 맞다/틀리다 정하는 일 |
| 턴 | 아이가 한 번 말하고 AI 가 한 번 답하는 한 묶음 |
| 대사 규칙 위반 | 캐릭터 AI 가 아이에게 한 말이 "이런 말은 하지 말 것" 규칙을 어긴 것 (옛 이름: 위반율 — 규칙 2-9) |
| 분석 정확도 | 아이가 한 말을 AI 가 제대로 알아들었는지, 정답지와 맞춰 본 비율 |

> **근거** — GOV.UK 쉬운 말 지침: *"전문용어가 필요하면 써도 된다. 처음 쓸 때 쉬운 말로 뜻을
> 설명하기만 하면 된다."* 같은 지침이 인용한 연구에서 **80% 가 쉬운 영어를 선호했고, 전문성이
> 높을수록 그 선호가 더 강했다** — 쉽게 쓰는 것은 전문가에게 손해가 아니다.

### 규칙 2-9. 닮은 두 채점을 **이름으로** 가른다

우리에게는 AI 를 채점하는 장치가 둘이고, 지금 화면은 둘 다 그냥 「채점」이라고 부른다.

| 무엇을 재나 | 만드는 곳 | 정답지 | 화면에서 부를 이름 |
|---|---|---|---|
| 캐릭터 AI 의 **대사**가 하면 안 되는 짓을 했나 | `lib/judge.ts` | 없어도 된다 | **대사 규칙 위반** |
| **아이 말 분석**이 맞았나 | `lib/scoring.ts` (골든셋) | 있다 | **분석 정확도** |

두 숫자를 한 화면에 같이 놓을 때는 반드시 이 두 이름으로 적는다.

> **근거** — 이 혼동은 **이미 두 번 일어났다.** `lib/judge.ts` 머리말이 첫 번째를 기록해 두었다:
> *"이름이 닮았지만 하는 일이 전혀 다르다. 8차 인계가 실제로 여기서 한 번 속아 「채점기가 절반
> 왔다」고 잘못 셌다."* 두 번째는 2026-08-14 이 문서를 만들며 한 인터뷰였다 — 팀에서 가장 이
> 코드를 잘 아는 사람도 「위반율」이 어느 쪽인지에서 갈렸다. **팀도 헷갈리는 것을 운영자가 가릴
> 수는 없다.** 설명문을 붙이는 것으로는 부족하고 이름 자체를 갈라야 한다.

### 규칙 2-3. 한 문장에 한 생각. 중요한 말을 앞에

- ✗ "이 화면에서는 프롬프트 파일을 고치지 않으며, 실험 내용은 고른 회차에만 저장되고 확정 내용은
  사람이 파일로 옮깁니다."
- ✓ "여기서 고친 내용은 **고른 회차에만** 적용됩니다. 원본 파일은 바뀌지 않습니다."

> **근거** — GOV.UK: *"한 문장에 한 생각. 중요한 말을 앞에 놓고 불필요한 말을 뺀다."*
> 예: 「총 비용입니다」가 아니라 「총 비용」, 「비밀번호를 잘못 입력하셨습니다」가 아니라 「비밀번호가 틀렸습니다」.

### 규칙 2-4. 설명이 아니라 **행동**을 적는다

- ✗ "`story_sessions` 한 행과 `runs` 한 행이 함께 생기고, 대화 장면에 닿을 때까지 전개를 재생한다"
- ✓ "시작을 누르면 이야기가 대화 장면까지 자동으로 진행됩니다. 30초쯤 걸립니다."

> **근거** — 견본(voice-test)의 "대사를 누르면 아래 TTS 입력에 텍스트·보이스·말투 지시가
> 채워집니다" 가 이 형태다. 구현이 아니라 **다음에 무슨 일이 일어나는지**를 적는다.

### 규칙 2-5. 화면에 쓰지 않는 것

| 금지 | 이유 |
|---|---|
| 코드 인용(백틱), 파일 경로, 함수명 | 운영자가 읽을 수 없다 (진단4) |
| ⛔ 🔴 ⚠️ 같은 코드 주석용 기호 | 코드 주석의 약속이지 화면 언어가 아니다 (진단5) |
| `null` · `undefined` · `true`/`false` | 「없음」 「아직 안 끝남」 「예/아니오」로 (진단2) |
| 개발자만 할 수 있는 조치 안내 | "npx tsx db/seed.ts 로 시드를 넣어라" → 운영자는 못 한다 (진단7) |
| 「색깔·위치」로만 가리키기 | "왼쪽 메뉴에서", "초록 버튼을 누르세요" |

> **근거** — 마지막 항목은 GOV.UK: *"모양·크기·색·위치만으로 정보를 전달하지 마라. 모든 사용자가
> 그 기준을 공유하지 않는다."* (색각 이상·화면 낭독기 사용자 포함)

### 규칙 2-6. 말투는 존댓말 평서형으로 통일

「…합니다 / …됩니다 / …하세요」. 반말·명령형("…없다", "…넣어라")을 섞지 않는다.

> **근거** — 진단6. 지금 화면마다 말투가 달라 한 제품으로 안 읽힌다. 코드 주석은 지금의 단정한
> 반말을 유지한다 — **주석은 개발자가 읽고, 화면은 운영자가 읽는다.**

### 규칙 2-7. 재미있게 쓰지 않는다

농담·감탄사·과장을 넣지 않는다. 지루하게 쓴다.

> **근거** — GOV.UK: *"글이 눈에 띄지 않는다면 제대로 쓴 것이다. 지루한 것을 목표로 하라."*

### 규칙 2-8. 설명이 길어지면 화면을 고친다

안내문 3문장으로 안 되면 글이 아니라 화면 구조가 문제다.

> **근거** — GOV.UK: *"인터페이스가 어떻게 동작하는지 설명해야 한다면, 그건 뭔가 잘못됐다는 신호다.
> 설명이 필요 없도록 인터페이스를 고쳐라."*

## 5. 상태·오류·위험동작

### 규칙 3-1. 결과에는 늘 수치를 붙인다

AI 를 부른 결과에는 **얼마나 걸렸는지 · 무엇으로 돌렸는지 · 얼마나 썼는지**를 함께 보여준다.

| 자리 | 붙일 수치 |
|---|---|
| 회차 상세 | 총 소요시간, 쓴 모델, 총 토큰, 대략 비용 |
| LLM 시도 상세 | 모델명, 생각 깊이, 소요시간(ms), 토큰 수, 비용 |
| 골든셋 결과 | 채점한 건수, 걸린 시간, 판정 불가 건수 |
| 음성(TTS/STT) | 소요시간(ms), 용량(KB), 쓴 모델 |

> **근거** — 견본(voice-test)이 합성 결과에 `ms`·`KB`·모델명을 붙인다. Braintrust 도 LLM 한 번
> 호출마다 모델·파라미터·토큰 수·소요시간·캐시 여부·추정 비용을 함께 보여준다. 수치가 없으면
> "왜 느리지 / 왜 비싸지"를 화면 밖에서 알아내야 한다.

### 규칙 3-2. 상태는 네 갈래로 구분해 보여준다

| 상태 | 표시 |
|---|---|
| 아직 안 함 | 회색 「아직 안 돌렸습니다」 |
| 도는 중 | 움직이는 표시 + **무엇을 하는 중인지** + 버튼 잠금 |
| 성공 | 결과 + 수치(규칙 3-1) |
| 실패 | 규칙 3-4 |

"도는 중"과 "실패"를 절대 같게 그리지 않는다.

> **근거** — 2026-08-13 사고: 도는 중인 턴을 「분석 단계에서 끊겼다」로 그렸고, 그 안내가 가리킨
> 「이어 돌리기」 버튼은 화면에 없었다(`runs/ui.tsx:130-148`). **없는 버튼을 가리키는 막다른 길**이었다.

### 규칙 3-3. 빈 화면은 다음 행동을 알려준다

「아직 없다」로 끝내지 않고 무엇을 하면 되는지 적는다.
- ✗ "아직 돌린 회차가 없다."
- ✓ "아직 진행한 회차가 없습니다. 위 「회차 시작」에서 이야기를 골라 시작해 보세요."

### 규칙 3-4. 오류 메시지 3단

① 무엇이 안 됐는지 ② 왜 그런지(아는 경우) ③ 지금 무엇을 하면 되는지 — **읽는 사람이 할 수 있는
조치로.** 개발자용 원문은 그 아래 접어 둔다.

```
✗  stories 가 비었다. npx tsx db/seed.ts 로 시드를 넣어라.

✓  이야기 목록이 비어 있어 회차를 시작할 수 없습니다.
   앱에 이야기 자료가 아직 심어지지 않았습니다. 개발 담당자에게 알려 주세요.
   ▸ 개발자용 원문 보기
```

> **근거** — GOV.UK: 오류 메시지에 「죄송합니다」는 넣지 않되(서비스가 통째로 멈춘 경우는 예외),
> 무엇이 잘못됐는지는 짧고 분명하게. 진단7 이 이 규칙의 반대 사례다.

### 규칙 3-5. 위험동작 — **확인창을 쓰지 않는다** ⭐ 결정

이 이슈에서 정해야 했던 항목(D10)이다. **결론: 확인창도 읽기전용 모드도 만들지 않는다**
(2026-08-14 결정). 대신 세 가지로 충분하다고 본다.

1. **버튼 글자에 무슨 일이 일어나는지 적는다** (규칙 3-6)
2. **누르면 즉시 잠근다** (규칙 3-7 — 이미 구현되어 있다)
3. **끝나면 걸린 시간과 비용을 보여준다** (규칙 3-1)

**왜 확인창이 없어도 되나** — 우리 「위험 동작」의 실제 피해가 작기 때문이다.

| 동작 | 최악의 경우 | 이미 있는 안전장치 |
|---|---|---|
| 회차 시작 (`/runs`) | 쓸데없는 회차 하나가 생기고 그만큼 AI 요금 | 버튼이 눌린 순간 잠긴다 |
| 골든셋 전체 채점 | 채점 한 판이 헛돈다 | 「몇 건까지」 상한이 이미 있다 |
| 시드 셀 저장 (`/seed`) | — | 되돌리기가 **이미 있다** (`undoSeedRevisionAction`) |
| 기준 남기기 (`/review/pending`) | — | 초안(draft)으로만 저장돼 정본을 안 건드린다 |
| 프롬프트 실험 저장 (`/prompt-lab`) | — | 고른 회차에만 적용되고 원본 파일은 그대로다 |
| 검수 판정 (`/review`) | — | 다시 검수해 덮어쓸 수 있다 |

아래 넷은 원래 되돌릴 수 있고, 위 둘은 되돌릴 수 없지만 **잃는 것이 회차 하나 / 채점 한 판**이다.
사람이 다치거나 자료가 사라지는 일이 아니다.

> **근거와 맞바꾼 것** — 참고한 지침들은 이보다 보수적이다. GNOME 인터페이스 지침은 *"되돌릴 수
> 없는 동작에는 확인창이나 되돌리기 중 하나가 반드시 따라야 한다"* 고 하고, NN/g 는 확인창이
> 무엇을 할 것인지 구체적으로 다시 말해야 한다고 한다.
> 우리는 **일부러 그보다 가볍게 간다.** 같은 GNOME 지침이 그 이유도 준다 — *"사람들은 확인창을
> 읽지 않고 습관적으로 눌러 넘긴다."* 피해가 작은 동작에 확인창을 달면, 정작 중요한 확인창이
> 생겼을 때 그것도 습관적으로 눌리게 된다. 그리고 이 도구의 성격상 **되풀이해서 돌려 보는 것이
> 정상 사용**이라(회차를 여러 번 돌려 견주는 것이 존재 이유다), 매번 확인창을 띄우면 본래 용도를
> 방해한다.
>
> ⚠️ **이 결정이 뒤집혀야 할 때**: 지우는 버튼이 생기거나(회차 삭제·골든셋 삭제), 한 번 눌러
> 나가는 돈이 눈에 띄게 커지면 이 규칙을 다시 연다.

**읽기전용 모드도 만들지 않는다.** 운영자가 못 보는 화면이 생기면 시연 가치가 떨어지고 구현도
늘어난다. 운영자가 직접 눌러 보는 것이 이 화면의 목적이다(D6).

### 규칙 3-6. AI 를 부르는 버튼은 색**과** 글자로 구분한다

확인창을 안 쓰기로 했으므로(규칙 3-5), **버튼 글자가 유일한 예고**다. 반드시 무슨 일이 일어나는지
적고, 다른 색을 함께 쓴다.

- ✗ 「시작」 → ✓ 「회차 시작 (AI 호출)」
- ✗ 「전체 돌리기」 → ✓ 「정답지 전체 채점 (AI 호출)」

> **근거** — GOV.UK: 색이나 위치만으로 정보를 전달하지 않는다. 색각 이상이 있거나 화면 낭독기를
> 쓰는 사람에게는 색 구분이 전달되지 않는다. 그래서 색**만**으로는 안 되고 글자가 함께 가야 한다.

### 규칙 3-7. 누르면 즉시 잠근다

제출 버튼은 눌린 순간 잠기고 「…하는 중」으로 바뀐다.

> **근거** — 2026-08-13 에 「시작」이 두 번 눌려 회차가 둘 생겼다(`runs/page.tsx:112`). 이미
> `보내기` 컴포넌트가 이 일을 하고 있으니, **다른 화면의 제출 버튼에도 같은 것을 쓴다.**

않았고, 두 콘솔 모두 로그인이 필요하다. 대신 두 곳의 **공식 문서**와, 화면 구조를 글로 서술한
다른 도구들(Braintrust · waza · MLflow)의 문서를 근거로 삼았다. 실제 화면을 본 뒤 규칙 1-6(요약
카드)과 1-4(설정 접기)는 더 다듬을 수 있다.
