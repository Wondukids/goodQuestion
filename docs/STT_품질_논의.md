# STT 품질 논의 — 소음과 아이 발음이 그대로 들어가는 문제

> 2026-08-15 · 아직 결정된 것 없음. 고를 것을 늘어놓은 논의 문서다.

## ⓪ 배경 — 지금 무슨 일이 벌어지나

**STT**(Speech-to-Text, 받아쓰기)는 마이크로 들어온 소리를 글자로 바꿔 주는 것이다. 우리 앱에서
아이가 마이크에 대고 말하면, 그 소리가 구글 서버로 가서 글자가 되어 돌아오고, 그 **글자만**
가지고 뒤의 모든 것이 돌아간다 — 캐릭터가 무슨 말을 할지, 아이가 어떤 생각을 했는지, 보호자
리포트에 뭐라고 적힐지.

문제는 STT 가 **소리를 가리지 못한다**는 것이다. 옆에서 엄마가 말하든, TV 가 켜져 있든, 아이가
「방귀」를 「방구」라고 하든, STT 는 들리는 대로 글자를 만들어 돌려준다. 그 글자가 아이 말인지
아닌지 우리는 지금 **알 방법이 없고**, 그대로 뒤로 흘러간다.

이 문서는 그 구멍이 어디에 몇 개인지 짚고, 막을 수 있는 자리를 층별로 늘어놓는다.

### 마이크 버튼 — 화면마다 다르다 🔴

이게 이 논의에서 제일 중요한 사실인데, 네 화면이 **서로 다르게** 동작한다.

| 화면 | 녹음 **시작** | 녹음 **끝** | 한도 |
| --- | --- | --- | --- |
| 대화 씬 (`interactive-scene.tsx:605·554`) | 🔴 **자동** — 캐릭터 질문 음성이 끝나는 순간 열린다 | 마이크 버튼 또는 만료 | 20초 |
| 미션1 (`mission1.tsx:359`) | 아이가 마이크를 **눌러야** 시작 | 다시 누르거나 만료 | 20초 |
| 미션2 (`mission2.tsx:382`) | 아이가 마이크를 **눌러야** 시작 | 다시 누르거나 만료 | 20초 |
| 후활동 줄거리 말하기 (`finale.tsx:521`) | 아이가 마이크를 **눌러야** 시작 | 다시 누르고, 그 뒤 「보내기」를 또 눌러야 전송 | 55초 |

즉 **미션·후활동은 시작과 끝을 둘 다 아이가 쥐고 있다.** 후활동은 보내기 전에 다시 녹음할 수도
있다(미리 듣기는 없다 — `finale.tsx:379` 는 소리를 들고만 있다가 보내기에서 STT 를 부른다).

**대화 씬만 자동 시작이다.**

### 정리하면

지금의 유일한 **자동** 문턱은 「글자가 비었나」 하나다. 글자가 한 자라도 있으면 그게 소음이든
옆 사람 말이든 전부 LLM 파이프라인을 타고, 말풍선에 뜨고, DB 에 남고, 리포트로 간다.
버튼은 아이가 눌러 줄 때만 도와주는 **수동** 문턱이다.

## 2. 새는 자리 세 군데

### (a) 마이크가 열려 있는 구간이 아이 발화보다 넓다 — **앞쪽**이 문제다

> ⚠️ 2026-08-15 수정. 처음엔 「말 끝나고 17초가 계속 녹음된다」로 적었는데, **끝은 버튼이
> 막고 있다.** 위 표를 확인한 뒤 좁혔다.

버튼이 막아 주는 것과 못 막는 것을 갈라 보면 이렇다.

**버튼이 막는 것 — 뒤쪽.** 아이가 「다 말했어요」를 누르면 그 순간 녹음이 끊긴다. 미션·후활동은
시작까지 아이가 쥐고 있어서, **아이가 버튼을 제대로 쓰는 한 이 화면들에는 (a) 가 거의 없다.**

**버튼이 못 막는 것 — 셋.**

1. 🔴 **대화 씬의 앞머리.** 대화 씬만 자동 시작이라, 캐릭터 질문이 끝나는 순간 마이크가 열린다.
   아이가 생각하는 몇 초, 그리고 그 사이 옆에서 엄마가 「뭐라고 말해야 하지?」 하는 것이
   **녹음 앞머리에 그대로 붙는다.** 버튼으로는 손댈 수 없는 구간이다.
2. **아이가 버튼을 안 눌렀을 때의 만료 구간.** 이때만 20초(후활동은 55초)가 통째로 간다.
   6~9세가 매번 누르는지는 **실기로 재 본 적이 없다** — 이 문서에서 숫자로 뒷받침 못 하는 유일한
   대목이고, Q1 로 묻는 이유다.
3. **말하는 도중의 소음.** TV·형제 목소리는 버튼과 무관하게 섞인다.

결국 (a) 는 「늘 17초가 붙는다」가 아니라 **「대화 씬 앞머리 + 안 눌렀을 때」로 좁혀진다.**
아래 A 갈래의 무게도 그만큼 줄었다.

### (b) 발음이 뭉개지면 엉뚱한 글자가 되고, 그게 조용히 지나간다

「며느리」→「메느리」, 「우수수」→「우수」처럼 뭉개진 것은 STT 가 **자신 있게** 다른 단어로
적어 준다. 그러면:

- 대화에서는 분석 LLM 이 뜻을 못 읽어 `UNCLEAR` 가 되고 → 되묻는다. **여기까지는 그럭저럭 된다.**
- 후활동 단어 판정(`post-activity/domain/keywords.ts`)에서는 **글자 대조가 먼저 돈다.** 「방구」는
  「방귀」와 글자가 달라 ① 규칙이 못 찾고, ②의 LLM 프롬프트(`prompts/retelling_keywords/보낼것.md`)는
  **「뜻이 들어 있나」만 보라고 되어 있지 「소리가 비슷한가」는 한 줄도 없다.** → `missing` 으로
  떨어진다. 아이는 말했는데 보호자 화면에는 「안 쓴 단어」로 뜬다.

### (c) 소음이 「그럴듯한 문장」이 되면 아무도 못 잡는다

가장 위험한 갈래다. 옆 사람 말이 통째로 들어와 문법에 맞는 한국어 문장이 되면, 분석 LLM 은
그것을 **멀쩡한 발화(`VALID`)로 읽는다.** 뜻이 통하니까. 소리 쪽 정보(음량·신뢰도·누가 말했나)가
LLM 에게 **전혀 전달되지 않기 때문에** 걸러 낼 근거 자체가 없다.

## 4. 추천 순서

> 🔴 마이크 버튼을 확인한 뒤 **순서를 바꿨다.** 전에는 A 갈래가 1순위였는데, 버튼이 뒤쪽을
> 이미 막고 있어서 A 의 몫이 줄었다.

1. **C3 ⑴ + A4** — 각각 프롬프트 한 줄, 코드 한 줄. 오늘 넣을 수 있고 되돌리기도 쉽다.
   C3 는 후활동에서 아이가 말했는데 「안 썼다」로 뜨는 것을 바로 줄인다.
2. **B2 + C1** — 신뢰도를 회수해서 문턱으로 쓴다. 「글자가 비었나」 하나뿐인 **자동** 문턱이
   둘이 된다. 버튼이 없는 자리(대화 씬 자동 시작)도 이건 막아 준다.
3. **A5** — 앞뒤 무음 잘라내기. (a) 에서 유일하게 남은 진짜 구멍인 대화 씬 앞머리를 막는다.
4. **D1** — 여기까지 하고도 남는 오인식이 얼마인지 재고, 그 숫자로 **B1(단어 힌트)** 과
   **B4(엔진 교체)** 를 결정한다.

⚠️ B4(엔진 교체)를 1순위로 두고 싶어지지만, 소음이 섞인 채로 엔진만 바꾸면 **더 좋은 엔진이
엄마 목소리를 더 정확하게 받아쓴다.** 순서가 뒤집히면 안 되는 이유다.

| **B1** | `speechContexts` (단어 힌트) | ❌ **안 바뀐다.** 같은 구글 STT v1, 같은 호출, `config` 에 키 하나 추가 |
| **B2** | `maxAlternatives: 3~5` + `confidence` 받기 | ❌ **안 바뀐다.** 같은 자리에 키 하나 더 |

이게 중요한 이유는 **둘 다 교정 방향에 그대로 보탬이 되기 때문**이다.

- **B1 은 교정 LLM 이 하려는 일을 더 싸고 더 안전하게 한다.** 「며느리」·「방귀」·「배나무」를
  힌트로 주면 구글이 **애초에 그렇게 받아쓴다.** LLM 교정과 결정적으로 다른 점은,
  구글은 **자기가 들은 소리의 후보 중에서 고를 뿐 없는 말을 만들지 않는다**는 것이다.
- **B2 는 교정의 재료가 된다.** 후보를 3~5개 받아 교정하는 LLM 에게 **같이 넘기면**,
  「1위: 메느리가 방구를 / 2위: 며느리가 방귀를」 중에서 **고르기만** 하면 된다.
  지어낼 필요가 없어진다. **교정 방향에서 가장 값싼 보강이다.**

→ 교정할 거리를 **줄여 놓고** 교정하는 것과, 안 줄이고 교정하는 것은 다르다. B1·B2 가 먼저다.

### 두 안

| | 안 1 — 교정을 따로 | 안 2 — 분석 LLM 이 교정도 함께 |
| --- | --- | --- |
| 흐름 | STT → **교정 LLM** → 분석 → 판단 → 대사 | STT → **분석 LLM(교정 포함)** → 교정본을 채팅에 먼저 띄움 → 판단 → 대사 |
| LLM 호출 | 턴마다 **+1** (2회 → 3회) | **+0** (필드 하나 추가) |
| 아이 말풍선 | 지금처럼 전부 끝나야 뜬다 | 분석이 끝나는 시점에 **먼저** 뜬다 |
| 건드리는 것 | 파이프라인 앞에 한 칸 | 분석 프롬프트 + **턴 API 계약** |

**대화 씬에서는 2안이 맞다.** 근거 셋:

1. 분석 LLM 은 이미 발화 전문을 읽고 있고, `main_point`(아이 말을 어른 문장으로 다시 쓴 것)를
   **이미 내고 있다.** 교정에 필요한 재료가 그 프롬프트 안에 전부 있다. 필드 하나면 된다.
2. 지금도 턴 하나에 LLM 왕복 2회 + TTS 다. 여기에 하나 더 붙이면 아이가 그만큼 더 기다린다.
3. 🔴 **2안의 진짜 값어치는 교정이 아니라 지연 해소다.** 지금은 `child.text` 와 `dialogue.text` 가
   **한 응답에 같이 실려서**(`session/service/turn.ts:117`), 아이는 자기가 말한 것이 화면에 뜨는
   것조차 대사 LLM 이 끝날 때까지 기다린다(`interactive-scene.tsx:515`). 분석이 끝난 시점에
   아이 말풍선을 먼저 띄우면 체감이 크게 달라진다.

**다만 2안은 턴 API 계약을 건드린다.** 지금은 요청 1번 = 응답 1번이다(명세 4.3절). 말풍선을
먼저 띄우려면 응답을 둘로 쪼개야 하는데,

- **스트리밍(SSE)** — 한 요청 안에서 두 번 흘려보낸다. 미완 턴 문지기와 안 부딪힌다. ✅ 추천
- 호출을 둘로 나누기 — ⛔ **미완 턴(`TURN_INCOMPLETE`) 문지기와 부딪힌다.** 지금 구조는
  「턴은 끝까지 돌거나 미완으로 남는다」인데, 반쪽 응답을 정상 상태로 만들면 그 문지기의
  뜻이 흔들린다.

**후활동 줄거리 말하기에서는 1안이 자연스럽다.** 기다리게 할 캐릭터 대사가 아예 없고, 이미
「보내기」를 누른 뒤의 처리 화면이 있다. 그리고 교정이 여기서 제일 크게 듣는다 — 단어 판정
①단계가 **글자 대조**라(`post-activity/domain/keywords.ts:71`) 교정 한 번에 적중률이 올라간다.

→ **두 안은 배타적이지 않다. 화면마다 다르게 고르면 된다.**

### ⚠️ 두 안 모두 못 푸는 것 둘

**(1) 교정은 (b) 를 고치고 (c) 를 악화시킨다.**

- (b) 발음 뭉개짐 — 「메느리가 방구를 뀌었어요」 → 「며느리가 방귀를 뀌었어요」. 잘 고쳐진다. ✅
- (c) 옆 사람 말이 통째로 들어온 것 — 「그거 말고 다른 거 말해봐」는 **이미 멀쩡한 문장이라**
  교정 LLM 이 그대로 통과시키거나 더 매끄럽게 다듬는다. 소리 정보가 없으니 아이 말인지
  아닌지 알 방법이 **원리적으로 없다.** 🔴 오히려 「어딘가 이상해 보이던 것」이 「말끔한
  문장」이 되어 **사람 눈에도 안 걸리게 된다.**

→ 교정으로 가더라도 (c) 는 따로 막아야 하고, 실마리는 소리 쪽 신호(신뢰도 B2 · 음량 A3)뿐이다.
**이건 LLM 으로 못 푼다.**

**(2) 무엇을 정본으로 삼을 것인가 — 스키마에 이미 자리가 있다**

`messages.stt_raw_text` 가 **이미 있다**(`sql/001_schema.sql:259`, 주석까지 「아이 발화에만
저장한다」). 그런데 **본 대화에서는 아무도 안 쓴다 — 늘 `null` 이다.** 즉 이 설계는 처음부터
「`text` = 정본, `stt_raw_text` = 받아쓴 원본」을 예상하고 만들어졌다. **교정 방향이 스키마와
어긋나지 않는다는 뜻이라, 2안에 유리한 사실이다.**

문제는 그 다음이다. **보호자 리포트는 `messages.text` 를 읽는다**(`report/repo/materials.ts:143`).
교정본을 `text` 에 넣으면 「아이가 이렇게 말했어요」 인용이 **교정본**이 된다.

- 교정본을 보여준다 → 읽기 좋다. 하지만 **아이가 실제로 안 한 말이 인용으로 나갈 수 있다.**
- 원본을 보여준다 → 정직하다. 하지만 지금의 「우리 애가 이렇게 말 안 했는데」가 그대로 남는다.

**추천: 인용은 원본, 판정·지표는 교정본.** 보호자에게 「아이가 이렇게 말했어요」로 나가는 글은
거짓이면 안 되고, 요소 감지·단어 판정은 뭉개진 발음 때문에 놓치면 안 된다. 다만 그러면
리포트 인용 대조기(`낱말이_발화에_있나`)가 **어느 쪽 글자를 보는지** 정해야 한다 — 지금은
`text` 하나만 본다.

⚠️ 후활동은 더 예민하다. `근거가_원문에_있나()` 가 지어낸 근거를 막는 **방어선**인데
(`keywords.ts:86`), 교정본을 원문으로 삼으면 **LLM 이 교정한 글자에 LLM 이 근거를 대는** 꼴이
된다. 자기가 만든 글자를 자기가 인용하는 것이라 방어선이 헐거워진다. → **후활동의 대조는
원본으로 하고, 교정본은 ①글자 대조를 한 번 더 돌리는 데만 쓰는 것**이 안전하다.
