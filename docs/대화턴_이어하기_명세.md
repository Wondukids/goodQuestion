# LLM 대화 턴 이어하기 — 기획·명세

> 2026-08-14 · `api_team` · 설계 문서 (구현 아님 — 이슈 등록용)
>
> **스코프: 대화 턴 하나의 이어하기.** 이야기 전체의 이어하기(진행 중 세션 찾기 ·
> 어느 장면부터 다시 보나)가 아니다 — 그쪽은 별도 이슈다 (7절 비스코프).

## 0. 배경 — 왜 이 문서인가

대화 장면에서 아이 발화 하나는 서버 안에서 **받아쓰기(STT) → 분석(LLM) → 판단(순수 함수)
→ 대사(LLM)** 네 단계를 돈다. 중간에 LLM 호출이 실패하거나 앱이 죽으면 턴이 **반쯤 저장된
채** 남는다 — 아이는 말했는데 캐릭터 대답이 없는 상태다. 그 반쪽 턴을 어떻게 살리는지가
이 문서의 전부다.

전체 이어하기 설계(설계 아티팩트 rev.2)에서 재개 지점을 「그 장면의 마지막 캐릭터
`messages` 행」으로 정했다. 캐릭터 대사가 안 나온 반쪽 턴은 그 규칙의 **유일한 구멍**이고,
이 문서가 그 구멍을 메운다.

## 1. 결정 — (가) 마저 돌린다

끊긴 턴은 **죽은 단계부터 이어 돌려** 캐릭터 대사를 만들어 내고, 그 대사가 재개 지점이 된다.

| 버린 안 | 왜 버렸나 |
|---|---|
| (나) 턴을 버리고 다시 말하게 한다 | 분석·판단이 끝난 턴은 턴 카운트와 판정이 이미 DB에 박혀 있다. 버리려면 되돌려야 하는데 `story_sessions` 는 매 턴 덮어써서 되돌릴 근거가 `turn_conditions` 에만 있다 — 복원 코드가 새로 필요하다 |
| (다) 무시하고 다음 발화를 받는다 | 턴 하나가 헛돌아 `max_turns` 에 일찍 닿는다 — 장면이 예정보다 일찍 끝난다 |

(가)의 값 둘: **끝난 단계(요금이 든 LLM 호출)를 다시 돌지 않는다.** 그리고 엔진에 이 동작이
이미 있다 — `resumeTurn()` (`src/llm/service/run.ts`). 이 이슈는 새 규칙을 만드는 것이
아니라 **그 동작을 아이 앱 계약으로 노출**하는 일이다.

## 2. 용어

- **턴**: 아이 발화 1건 + 그에 대한 캐릭터 대사 1건.
- **미완 턴**: 아이 `messages` 행은 있는데 그 턴의 캐릭터 대사 행이 아직 없는 턴.
- **죽은 단계(stage)**: 미완 턴이 멈춘 자리 — `analysis` · `decision` · `character`.

## 3. 미완 턴 판정 — 저장된 사실만 본다

메모리의 진행 표시는 근거가 아니다. 세션의 **마지막 아이 발화**를 기준으로:

| 저장된 행 | 죽은 단계 |
|---|---|
| `utterance_analyses` 가 없다 | `analysis` |
| 분석은 있는데 `turn_conditions` 가 없다 | `decision` |
| 판정은 있는데 **바로 다음 행**이 이 장면의 캐릭터 메시지가 아니다 | `character` |
| 다음 캐릭터 행이 있다 | 미완 아님 |

- ⚠️ 「바로 다음 **한 행**」을 본다. 화자를 걸러 집으면 실패한 턴이 다음 턴의 대사를
  자기 것으로 착각한다 (`pendingTurn()` 주석의 함정 그대로).
- **STT 실패·빈 발화는 미완 턴이 아니다.** 확정 텍스트가 없으면 `messages` 행 자체가
  안 생기므로(기존 규칙) 서버 상태가 하나도 안 변한다. 아이는 그냥 다시 말하면 된다.

## 4. API 계약 (아이 앱)

전제: 아이 앱 턴 API `POST /api/sessions/{session_id}/turns` (별도 이슈 — 요청 한 번 =
턴 하나). 그 계약에 이 문서가 둘을 더한다.

### 4.1 새 발화는 미완 턴에 막힌다

미완 턴이 있는 세션에 새 발화를 보내면 **409** 로 튕기고 미완 정보를 싣는다
(엔진의 기존 문지기 FR-035 와 같은 규칙):

```json
{ "ok": false, "error": {
    "code": "TURN_INCOMPLETE", "retryable": false,
    "pending": { "message_id": "…", "stage": "character" } } }
```

앱은 이걸 받으면 아래 resume 을 부른다.

### 4.2 `POST /api/sessions/{session_id}/turns/resume`

- 요청 body **없음**. 오디오를 다시 받지 않는다 — 발화는 저장된 그 문장이다.
- 동작: 죽은 단계부터 이어 돌린다 (5절).
- 성공 응답은 일반 턴 응답과 같은 모양 + `resumed_from`:

```json
{ "ok": true, "data": {
    "resumed_from": "character",
    "child":    { "message_id": "…", "text": "저장돼 있던 아이 발화" },
    "dialogue": { "message_id": "…", "text": "캐릭터 대사", "source": "generated" },
    "next":     { "kind": "발화받기", "scene_id": "…" } } }
```

| 상태 | code | 언제 | 재시도 |
|---|---|---|---|
| 404 | `SESSION_NOT_FOUND` | 세션이 없다 | ✕ |
| 409 | `TURN_NOT_ALLOWED` | 미완 턴이 없다 — 이어 돌릴 것이 없다 | ✕ |
| 409 | `TURN_IN_PROGRESS` | 같은 세션에 다른 호출이 도는 중 | ○ |
| 502 | `LLM_UNAVAILABLE` | 이어 돌리다 또 실패. 저장 상태는 그대로다 | ○ (다시 resume) |

**반복 안전하다**: 성공하면 미완이 사라져 두 번째 호출은 409 `TURN_NOT_ALLOWED`.
실패하면 상태가 안 변해 다시 불러도 같은 자리부터다.

### 4.3 세션 조회에 미완 턴을 싣는다 (연계)

이어하기 화면이 「마저 돌릴 게 있는지」를 알아야 한다. 세션 조회 응답(별도 이슈)에
`pending_turn: { message_id, stage } | null` 을 싣고, 앱은 세션 진입 시 값이 있으면
**resume 부터 부른 뒤** 그 대사를 재개 지점으로 보여 준다.

## 5. 재개 동작 — 단계별

| 죽은 단계 | 하는 일 | 다시 부르는 LLM |
|---|---|---|
| `analysis` | 저장된 아이 메시지 행을 **그대로 쓰고** 분석부터 끝까지 | 분석 + (CLOSING 아니면) 캐릭터 |
| `decision` | 저장된 분석을 후처리(순수 함수)해 **판정만 다시** 내고 대사로 | 캐릭터만 |
| `character` | 박제된 판정(`turn_conditions`)을 되살려 **대사만**. 재판정 금지 | 캐릭터만 |

### 불변 조건 — 어겨지면 버그다

1. 아이 `messages` 행을 새로 만들지 않는다 → 행 수·`turn_order`·턴 카운트 불변.
2. `character` 에서 죽은 턴은 **다시 판정하지 않는다** — 박제된 값 그대로 (재현성 · FR-016).
3. 이미 캐릭터 행이 있으면 **덮어쓴다**. 행을 늘리지 않는다.
4. 박제된 판정이 CLOSING 이면 캐릭터 LLM 을 부르지 않는다 — `character_closing` 고정 텍스트.
5. 실패한 시도도 `llm_calls` 에 남는다.
6. 세션 상태 갱신(턴 카운트 +1 포함)은 `decision` 단계의 커밋에만 있다 —
   resume 이 카운트를 두 번 올리는 경로가 없다.

## 6. 기존 코드 매핑 — 이 이슈에서 새로 쓰는 규칙은 0이다

| 명세 | 이미 있는 코드 (`src/llm/service/`) |
|---|---|
| 3절 미완 턴 판정 | `run.ts` `pendingTurn()` |
| 5절 죽은 단계부터 이어 돌리기 | `run.ts` `resumeTurn()` |
| 박제 판정 되살리기 | `run.ts` `restoreDecision()` + `repo` `readTurnCondition()` |
| 저장 분석 되살리기 | `repo` `readSavedAnalysis()` + `engine` `postProcess()` |
| 캐릭터 행 덮어쓰기 | `turn.ts` `runDialogueStage()` 의 덮어쓰기 갈래 |
| 4.1절 새 발화 문지기 | `step.ts` `analysisStep()` 의 `pendingTurn` 검사 |

새로 쓰는 것은 세션 도메인의 컨트롤러·서비스에서 위를 엮는 것과 응답 봉투뿐이다.

⚠️ 전제 하나: `resumeTurn()` 은 `run_id` 를 받는다. 세션 id → 회차 매핑은
`runOfSession()` 이 하는데, **아이 앱 세션에도 회차(`runs`) 행이 있어야** 이 길이 열린다
(세션 생성 시 `started_by='app'` 회차를 함께 만드는 결정 — 세션 도메인 이슈에서 확정).

## 7. 비스코프 — 이 이슈에서 하지 않는 것

- 이야기 수준 이어하기(진행 중 세션 찾기 · 재개 장면 조회 · 직전 영상 다시 보여주기) — 별도 이슈
- TTS·합성 오디오 저장 — 하지 않기로 결정됨 (rev.2)
- 같은 녹음 두 번 올라오는 것 막기(`client_turn_id`) — 별도 이슈
- 다중 인스턴스 잠금(메모리 `inProgress` → DB 잠금) — 별도 이슈. 이 명세는 단일 인스턴스 전제

## 8. 수용 기준 — 이게 다 초록이면 끝난 것이다

1. 캐릭터 단계를 강제 실패시킨 뒤 resume → 200 · `resumed_from=character` ·
   턴 카운트와 `turn_conditions` 불변 · 캐릭터 대사 행이 생긴다.
2. 분석 단계를 강제 실패시킨 뒤 resume → 아이 `messages` 행 수 불변(재사용) · 분석~대사 완주.
3. 미완 턴 없이 resume → 409 `TURN_NOT_ALLOWED`.
4. 미완 턴이 있는 세션에 새 발화 → 409 `TURN_INCOMPLETE` + pending 정보.
5. resume 성공 직후 resume 한 번 더 → 409 (반복 안전의 정의).
6. CLOSING 판정이 박제된 턴을 resume → `source=fixed` · LLM 호출 없음 · `next.kind=장면끝`.

## 9. 열린 질문

- 앱이 resume 을 **자동으로**(세션 진입 시) 부르나, 이어하기 버튼 뒤에 부르나 —
  화면 정책이다. 서버 계약은 어느 쪽이든 같다.
- `resumed_from` 을 앱이 쓸 일이 있나 — 없으면 로그용으로만 남긴다.
