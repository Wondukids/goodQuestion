## 부모 이슈

**제목:** `관리자 페이지 UI/UX 개선 — AI 관리도구 설계 원칙을 배우며`

**본문:**

### 배경

`(admin)` 여섯 화면(회차·시드 작업대·검수·골든셋·캐릭터 보기·프롬프트 작업대)은 "엔진을 눈으로
확인하는 최소 도구"로 만들어져, 작은 글씨·회색 기본값·개발자 시점(AI가 쓴) 설명문으로 되어 있다.

이 MVP는 해커톤에 내고, **해커톤 운영자(AI 비전공자)가 관리자 화면을 직접 클릭해 볼 수 있어야 한다.**
지금 상태로는 정보 밀도·설명문·글자 크기 모두 그 눈높이에 불친절하다.

반면 `/dev/voice-test`(STT·TTS 테스트 페이지)는 잘 만든 견본이다 — 카드 단위 구획, 큰 글자와
넉넉한 여백, "대사를 누르면 아래 입력이 채워집니다" 같은 행동 중심 안내문, 결과에 소요시간(ms)·
용량(KB)·모델명 동반. 이 강점을 규칙으로 추출해 관리자 전체에 적용한다.

### 목표 (두 겹)

1. **화면 개선** — 여섯 화면 + 공통 뼈대를, 일반 성인 누구나 읽고 조작할 수 있게 고친다.
2. **학습** — AI 서비스 관리도구(LLM·TTS·STT 콘솔)의 설계 원칙을 벤치마킹으로 배우고,
   그 결과를 `docs/관리자_디자인_규칙.md` 로 남긴다. 이후 모든 구현 PR은 이 문서의 규칙 번호를 인용한다.

### 원칙 (인터뷰 확정)

- 설명문 눈높이는 **일반 성인 누구나** — 내부 용어(골든셋·시드·회차·프롬프트…)는 전부 생활어로 풀이.
- Tailwind만 쓴다. 새 라이브러리·빌드 도구 없음.
- 제품 디자인 토큰(`bg-surface`, `text-ink`, `shadow-panel`…)을 관리자에도 재사용.
- "이 화면은 도구지 엔진이 아니다" 경계는 유지 — 보이는 것만 바꾸고 `lib/service/*` 호출 구조는 건드리지 않는다.
- 위험동작(시드 생성·검수 판정·골든셋 등록·LLM 호출) 보호 방식은 규칙 문서에서 결정.
- 마감 압박 없음 — 학습 충실 우선.

- [ ] #b 공통 뼈대 개선

### 완료 기준

## 하위 이슈 #a

**제목:** `관리자 디자인 규칙 문서 — AI 콘솔 벤치마킹으로 만든다`

**본문:**

### 하는 일

AI 서비스 관리 콘솔들을 조사해서, 우리 관리자 화면에 적용할 디자인 규칙 문서
`docs/관리자_디자인_규칙.md` 를 만든다. **이 이슈가 끝나야 #b·#c를 시작할 수 있다.**

### 조사 대상

- OpenAI 콘솔(플레이그라운드 포함), Google AI Studio — LLM 관리 화면의 표준.
- 조사하며 발굴 — "잘한다고 평가받는 관리도구 UI"를 만나면 추가 (음성 쪽 사례 포함, 예: ElevenLabs).
- 내부 견본: `/dev/voice-test` 강점 4가지 분석 — 카드 구획 · 큰 글자·여백 · 행동 중심 안내문 · 결과 수치 동반.
- 반면교사: 현재 `(admin)` 화면 — 무엇이 왜 불친절한지 진단.

### 규칙 문서의 장 구성

1. **화면 배치·정보 밀도** — 카드/표/여백/글자 크기, "한 화면에 얼마나 보여줄지"의 기준.
2. **설명문 글쓰기** — 일반 성인 눈높이. 용어 첫 등장 시 풀이, 금지 어휘, 행동 중심 문장, 예시 필수.
3. **상태·오류·위험동작** — 로딩·실패·성공 표시법, 위험 버튼(시드 생성·검수 판정·골든셋 등록·LLM 호출)
   보호 방식 결정: 시각 구분+확인창 vs 읽기전용 모드 — 벤치마킹 근거로 여기서 정한다.
4. **부록: 벤치마킹 근거** — 각 규칙이 어느 콘솔의 어떤 화면에서 왔는지.

### 진행 방식 (학습이 목적)

Claude가 조사와 초안을 만들되 **항목마다 '왜 이 규칙인지' 근거를 붙인다** → 사용자가 항목별로
질문·수정하며 함께 확정한다. 초안을 그대로 통과시키지 않는다.

### 완료 기준

- [ ] 규칙마다 번호가 있어 PR에서 인용 가능 (예: 규칙 2-3).
- [ ] 위 4개 장이 모두 있고, 위험동작 보호 방식이 결정되어 있다.
- [ ] 사용자 검토를 거쳐 확정됨.
