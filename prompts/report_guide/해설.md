# 보호자 리포트 · 가정 연계 가이드 프롬프트 — 해설

> ⛔ **이 파일은 LLM 에 한 글자도 안 간다.** 나가는 것은 옆의 `보낼것.md` 뿐이다.
>
> 규칙 한 덩이에 붙는 `[G-…]` 가 두 파일을 잇는다 — **같은 태그가 양쪽에 다 있어야
> 한다.** `tests/prompts.test.ts` 가 짝을 센다. ⚠️ 「태그는 양쪽에 있는데 뜻이 어긋난
> 것」은 검사가 못 잡는다. 두 파일을 나란히 놓고 사람이 봐야 한다.
>
> 관리 규칙 전체는 `prompts/README.md`.
>
> 정본: `docs/보호자_리포트_명세.md` 5.1·5.4·5.5 (이슈 #37 · 확정 결정 R7).

활동 하나가 끝난 뒤 보호자 리포트의 **가정 연계 가이드 탭**을 쓰는 프롬프트다.
시안 `23.png` 의 「골랐어요 한 줄 · 이야기 질문 3개 · 일상 질문 3개」가 여기서 나온다.
짝이 되는 `report_analysis` 는 말하기 분석 탭을 맡고, **둘은 서로를 안 본다** —
그래서 동시에 부른다 (명세 8절). 한쪽이 실패해도 다른 쪽은 산다 (결정 R9).

🔴 **질문 6개를 LLM 이 쓰는 이유** — 결정 R7. 「아이가 실제로 한 말을 이어받는 질문이라
아이마다 달라야 한다」. 고정 질문 목록이면 모든 아이가 같은 저녁을 보낸다.

## 받는 것

user 본문은 언제나 재료 JSON 한 덩이다 (`buildReportGuideMaterial()` —
`src/report/engine/material.ts`). 프롬프트는 그 글자를 한 번도 안 본다.

| 열쇠 | 무엇 |
|---|---|
| `child` | `name` · `age`. 이름은 프롬프트에 **넣는다** (결정 R12) |
| `missing_elements` | 이번 활동에서 모자랐던 요소 코드 목록 |
| `quotes` | 인용 후보. `message_id` · `scene_code` · `scene_label` · `text` · `elements` |

📄 명세 5.4 「받는 재료: 장면별 아이 발화(인용 후보) + 이번 활동에서 **모자랐던 요소** +
아이 이름·나이」 — **그 셋 그대로**다.

🔴 **`scene_label` 은 꼴이 하나가 아니다** (미정 M7 이 2026-08-15 에 확정됐다).
본 대화 발화면 「장면 3 · 들켜버린 큰 방귀」, 미션(미니게임) 발화면 「미션 · 배 따기」로
온다. 값을 만드는 것은 지표 집계기(이슈 #36)이고, 이쪽은 **화면에 그대로 찍을 이름표**로만
다룬다. 「장면 N ·」 꼴을 규칙으로 읽으면 미션 발화에 없는 장면 번호를 붙이므로
`보낼것.md` 머리에 「쪼개지도 다시 번호 매기지도 마라」를 박아 두었다.

### `missing_elements` 는 이 갈래가 만든다

명세가 「모자랐던 요소」라고만 적고 산식을 주지 않았다. 엔진이 `metrics.axes` 에서 뽑는다
(`모자란_요소()` — `src/report/engine/material.ts`). 규칙과 그 한계는 그 함수 머리말에 있다.

⚠️ **`REQUEST` 는 세지 않는다.** 결정 R4 가 「남는 `REQUEST` 는 뜻이 어긋나 쓰지
않는다」로 다섯 축에서 뺐기 때문에, `axes` 만 보면 `REQUEST` 는 **언제나 0** 이 되어
매번 모자란 요소로 뽑힌다. 그래서 산식에서 제외했다. 다만 `[G-ELEMENT]` 는 여덟 코드를
다 받는다 — 발화가 받쳐 주면 `REQUEST` 질문을 못 낼 이유는 없다.

## 태그별 해설

### `[G-PARENT]` · `[G-CHILDTALK]` 한 응답 안에 말투가 둘이다
📄 명세 5.5 「읽는 사람은 부모다」. 그런데 `question` 은 **부모가 아이에게 소리 내어
읽는 문장**이다 — 시안 예시가 "왜 부끄러웠을까? 이유까지 말해줄래?" 로 반말이다.
`reason` · `goal` 은 부모에게(해요체), `question` · `fallback` 안의 대사는 아이에게(반말).

🔴 **이 갈래에서 제일 자주 흔들릴 자리다.** 한쪽 말투로 통일하라고 하면 질문이
「~해 보도록 유도해 주세요」 꼴의 지시문이 되거나, 반대로 `goal` 이 아이에게 하는 말이
된다. 그래서 태그를 **둘로 갈라** 각각 어느 칸에 걸리는지 적어 두었다.
「한 번에 하나만 묻는다」는 캐릭터 프롬프트의 같은 규칙과 결이 같다.

### `[G-THREE]` 각 3개 고정
📄 명세 5.4 「각 배열은 3개 고정」. 프론트 계약 1절의 주석도 `// 3개` 다.
⚠️ 엔진이 인용 대조에서 질문을 **버릴 수 있어** 3개보다 적게 나갈 수 있다.
`[G-QUOTEID]` 를 볼 것.

### `[G-QUOTEID]` 인용은 글자가 아니라 id 로 오간다
📄 명세 5.2 의 대조 규칙이 이쪽에도 그대로 걸린다. 엔진이 `quotes[]` 밖의
`quote_message_id` 를 대조해 **그 질문을 통째로 버린다** (`src/report/engine/verify.ts`).

🔴 **여기만 말하기 분석 쪽과 처리가 다르다.** 카드는 인용을 `null` 로 비우고 카드를
남기지만, `StoryQuestion.quote_message_id` 는 프론트 계약 1절에서 **`null` 을 안 받는
칸**이라(`quote_message_id: string`) 비울 자리가 없다. 「엉뚱한 id 를 그대로 내보내기」와
「그 질문을 버리기」 중 **버리는 쪽**을 골랐다 — 프론트 계약이 「서버가 목록 밖 id 는
버리므로 **찾으면 반드시 있다**」에 기대어 `find()` 결과를 그대로 쓰기 때문이다.
질문 하나가 비는 것은 화면이 견디지만, 못 찾는 id 는 화면이 못 견딘다.

`scene_code` 를 「그 인용의 것」으로 못박은 이유도 같다. 배지에 찍히는 장면과 인용된
발화가 어긋나면 부모가 **다른 장면 이야기를 아이에게 묻게 된다.** 엔진이 인용에서
`scene_code` 를 다시 가져와 덮어쓴다 — 모델이 흘려도 화면은 안 어긋난다.

### `[G-FOLLOW]` · `[G-SPREAD]` 아이가 한 말에서 자란 질문
📄 명세 3.2 표 「① 카드의 요소 배지 · 장면 이름 · 아이 발화 인용 → 재료를 규칙이 주고
LLM 이 **고른다**」. 시안 ① 카드가 아이 발화를 인용문으로 보여 주고 그 아래 부모 질문을
붙이는 구성이라, 질문이 그 인용과 안 이어지면 카드 자체가 말이 안 된다.
`[G-SPREAD]` 를 따로 둔 것은 실측 없이 정한 예방책이다 — 인용 후보가 한 장면에 몰린
활동에서 세 질문이 같은 발화를 물고 늘어질 수 있다.

### `[G-ELEMENT]` 여덟 코드
📄 명세 5.4 「`element` 는 8요소 코드여야 하고, 배지 이름은 프론트가 `elementName()` 로
바꾼다」. 코드 목록은 `src/llm/elements.ts` 가 정본이다. 한국어 이름(감정·까닭…)을 내면
프론트의 `elementName()` 이 **모르는 코드를 그대로 돌려주므로**(그 함수 주석 참고)
배지에 「감정」이 아니라 「감정」이 그대로 찍히는 대신 다른 코드와 짝이 안 맞는다.
엔진이 여덟 코드가 아닌 값을 낸 질문은 버린다.

⚠️ 「질문이 겨냥하는 요소」와 「그 인용이 이미 담고 있던 요소」는 **다르다.** 안 갈라
두면 모델이 `quotes[].elements` 를 그대로 베껴 이미 잘한 것만 또 묻는다.

### `[G-MISSING]` 모자란 쪽을 먼저
📄 명세 5.4 재료에 「이번 활동에서 모자랐던 요소」가 들어가는 이유가 이것이다.
**강제가 아니라 선호**로 적었다 — 인용 후보가 그 요소를 받쳐 주지 못하는 활동이 있고,
억지로 맞추면 아이가 한 말과 상관없는 질문이 나온다.

### `[G-FALLBACK]` 「몰라」라고 할 때
📄 명세 5.4 예시 `"\"몰라\"라고 한다면 — \"지우라면 그때 어땠을 것 같아?\""` ·
시안 23 의 「대답이 짧을 땐 3단계」 카드와 같은 결. 꼴을 「조건 — 대사」로 못박은 것은
시안이 그 꼴로 찍기 때문이다.
🔴 **「더 쉬운 질문」이 조건이다.** 같은 질문을 말만 바꿔 다시 묻는 것이 가장 흔한
실패인데, 아이가 막힌 이유가 그대로 남아 두 번 막힌다. 먼 것(인물의 마음)을 가까운
것(내 경험)으로 바꾸는 방향을 적어 두었다.

### `[G-DAILY]` · `[G-GOAL]` 일상 질문 3개
📄 명세 3.2 표 「② 일상 질문 3개 + 목표 한 줄 → `narrative.daily_questions[]`」.
시안 예시 세 쌍이 전부 「내 경험과 이유 / 이해와 배려 / 결과 예상」 배지 + 「~해보기」
목표다. 이야기를 떠나라고 못박은 것은, 안 적으면 모델이 이야기 질문 3개를 말만 바꿔
여섯 개로 늘리기 때문이다. 배지 글자 수(2~8자)는 시안 배지 폭에서 왔다.

### `[G-REASON]` 골랐어요 한 줄
📄 명세 3.2 표 「"이유·결과를 묻는 질문으로 골랐어요" → `narrative.reason`」.
여섯 질문 **위에 하나**만 있는 문장이라 질문마다 붙는 설명이 아니다.

### `[G-NOGRADE]` · `[G-NOSTORY]` 두 프롬프트 공통 금지
📄 명세 5.5. 「평가·등수·진단 금지」와 「이야기 줄거리를 바꾸거나 없는 장면을 지어내지
않는다」. `report_analysis` 의 평가 금지·줄거리 금지 태그와 같은 규칙이고, 여기에
**「퀴즈가 아니다」 한 줄을 더했다** — 질문 여섯 개를 나열하면 모델이 정답이 있는 문제로
쓰기 쉽고, 그러면 부모가 아이를 시험 보게 된다.

## 프롬프트에서 뺀 것과 그 이유

| 뺀 것 | 왜 |
|---|---|
| 출력 JSON 모양 전체 | **출력 스키마로 나간다** (`src/report/engine/narrative.ts`). 모양을 두 곳에 적으면 갈라진다 |
| `metrics` 의 숫자·축·낱말 | 명세 5.4 의 재료 목록에 없다. 질문을 짓는 데 필요한 것은 **아이가 한 말**이지 몇 번 했나가 아니다 |
| `story_title` | 명세 5.4 재료 목록에 없다. 이야기 맥락은 `quotes[].scene_label` 과 `text` 가 이미 나른다 |
| 사고 요소 8종의 뜻 | 코드 이름만 있으면 되고, 뜻까지 주면 모델이 요소를 **다시 판정**하려 든다 |
| 「대답이 짧을 땐 3단계」 문구 | 프론트 상수다. 저장하지 않는다 (명세 3.2) |
